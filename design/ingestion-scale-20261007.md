# 长文档完整入库：可靠完成与效率 · N3 spec（2026-10-07）

方向：Claude；实现：Codex N3 会话，在独立 git worktree 分支开发，完成后由主线合并。开发准则 `AGENTS.md` 优先于本 spec。

## 问题（已脱敏的真实失败形态）

一份 225 页、310 张候选表的 A 股年报，按标准完整入库路径用 CPA gpt-6-luna（清洗 low）处理：

- **不会自己继续。** 10 次尝试只完成 12/310 张表。几乎每次运行推进约 1 张表就结束本轮，最后一次没有推进。程序知道还剩 298 张表，却要靠人工反复“继续”。
- **单表成本过高。** 136 次请求中，已知输入约 1410 万 token（缓存读取约 1300 万，未缓存约 110 万），输出约 3.2 万。平均每次请求的上下文约 10 万 token，每张表约 117 万输入 token。
- **分批过细。** 310 张表分成 310 批，每批 1 张。“模型写清洗规则、程序取数”的设计本可以让一份脚本覆盖一组结构相似的表，现在没有用上。
- **语义映射不完整。** 部分指标按行号命名，而不是按财务含义；部分列（构成比例、变动列）未映射。
- **工具错误。** set_document_profile 的主体识别失败（entity_not_grounded、entity_identifier_not_grounded），提交时出现指标与单位不匹配的校验错误。

对照历史：2026-10-05 瑞和 57 页中报 50/50 张表，首次无中途提示，约 14 分钟、106 次请求、缓存命中 97%。大文档上的表现明显退化。

**这份材料是评测的 held-out，N3 不得读取它的原文、入库数据、处理轨迹或参考答案。** 上述形态已足够定位问题，复现请用非 held-out 材料。

## 目标

完整入库能在无人值守的情况下跑完大年报，单表成本显著下降，语义映射完整。完整入库是保留功能，不缩小范围、不跳过表、不降低清洗要求（AGENTS.md）。

## 改动方向（具体实现由你决定，并以测量数据为依据）

1. **程序按进度续跑。**
   - 处理运行在模型结束本轮、而文档仍有未完成表时，由宿主用 Pi 原生的后续消息自动继续，并附紧凑的剩余工作描述，例如下一批表的 ID 和结构摘要。
   - 只有以下情况才停止：全部完成；一次续跑没有任何推进（报告原因与卡住的表）；用户取消；真实资源错误。
   - 不设固定调用次数上限，也不把进度记录变成模型必须阅读和确认的检查点。
2. **按结构分组成批。**
   - 程序按表头结构、列模式、所在章节，把结构相似的表归为一批。一份清洗脚本作用于整批，程序按坐标取数并逐表校验。
   - 批的大小按上下文预算和表规模动态决定。个别表校验失败只影响该表，不阻断同批其他表。
3. **上下文瘦身。**
   - 先实测每次请求的上下文构成：系统提示、工具说明、表内容、历史结果、重复载荷各占多少。
   - 去掉重复和不必要的载荷，保持稳定前缀以利缓存。表内容用紧凑视图，完整内容按需读取。
   - 不能靠静默裁剪必要证据来省 token。
4. **语义映射完整性。**
   - 指标 ID 按财务含义生成。行号式命名、未映射列由程序在提交前直接指出，并给出候选。
   - 构成比例、变动列按“比例/百分点/变动额”的语义列类型处理。真正无法判断的保留原文并标为待核验，不丢弃、不猜。
5. **主体识别。** 修正 entity_not_grounded 类失败：从封面、释义、页眉取主体与代码。报错信息给出可直接采用的候选。

   - 建议先用瑞和中报（有历史基线：50 张表、106 次请求）或卡罗特中报。

2. **改动后对比。** 同一材料改前与改后：完成率、是否需要人工继续、请求数、输入/未缓存/输出 token、用时、事实数，以及原格回放与原文抽查一致率。

## 第二轮（2026-10-08）：复用优先，降低单表成本，修正语义

第一轮结论：续跑能力已经能把小文档跑完，主线已合并上线。但大文档的单表成本仍然很高：伊利 37 页子集 51 张表约 1620 万输入 token，平均每表约 32 万。语义上也有硬错误：会计准则误标为 IFRS，102 条笼统的 `amount` 指标。继续压缩上下文是边际收益，根本办法是**不重复做已经做过的工作**（AGENTS.md：“已经完成且输入、规则和来源版本未变的工作应复用”）。

### 方向
1. **会计准则由程序判定。** 从原文措辞（例如“企业会计准则”“财政部”、IFRS/HKFRS 等）确定性识别，写入文档档案。模型只能在有原文证据时修改，修改时必须引用原句。
2. **标准报表确定性映射。** 中国企业会计准则通用格式下的合并与母公司资产负债表、利润表、现金流量表、所有者权益变动表的标准行项目，以及 IFRS/HKFRS 港股报表的常见行项目，用程序维护的行项目到指标的对照直接映射，不调用模型。匹配不到的行仍交给模型，保留原文，不丢弃。
3. **清洗规则库：按表结构签名复用。** 一批表的清洗规则提交并通过程序校验后，抽象成与具体文档无关的规则，例如表头语义、行标签到指标、单位和期间处理，以结构签名为键存入规则库。新表命中签名时直接应用规则，再走完全相同的程序校验；校验失败或未命中的表才交给模型。
   - 规则库只存映射规则，不存任何文档的数值或原文，项目隔离不受影响。
   - 规则带版本，规则变化时受影响的结果可追溯。
4. **处理顺序优先核心。**
   - 先处理三大表、主要会计数据、非经常性损益、现金流量补充资料、分季度数据、分部信息，再处理其余附注。只调整顺序，不缩小范围，全部表最终都要完成。
   - 核心部分完成时在状态中标明，让分析可以先开始。
5. **遗留问题。**
   - 瑞和最终运行因映射错误停止：单表映射失败只影响该表，其余表应继续推进。
   - 笼统的 `amount` 指标要按财务含义命名，程序在提交前直接指出并给出候选。

### 验收（迭代一律用 40 页以内的子集，最后只做一次完整中报）
1. 伊利 2024 同一个 37 页子集，与第一轮的 1620 万 token / 51 表对比：每表输入 token、未缓存 token、请求数、用时；会计准则是否正确；笼统指标数；原格回放；原文抽查不少于 20 处。
2. 复用测试：用贵州茅台 2024 年报（samples/native-pdf，不属于任何评测集）中与伊利子集对应的章节，跑同等规模的子集。报告规则库命中率、模型处理的表数、每表 token。这一项最能说明“第二份文档更便宜”。
3. 瑞和中报完整跑一次（50 张表），对比历史和第一轮结果。
4. 全部用量单列为资料准备研发支出。
5. 达标后给出“伊利 2024 全文”的预计 token 区间，再由我决定是否开跑。
