# 数值统一交付与新公司对照（2026-10-06）

本轮根据用户批准施工。保留完整入库、Pi 原生循环、权限边界和自定义 Python。此前伊利回归中“正文正确，图表小十倍，CSV 大十倍”作为已发生的交付错误保留，不改旧产物和成绩。

## 实现口径

- 现有 run_analysis 增加 report 输入，数值单元格引用记录或指定模型版本。一次换算后的 rows 同时生成图形、CSV、Markdown 数字占位符及 chart_data.json。普通展示不要求模型写搬运脚本；复杂计算可写 Python 后输出同一 report 对象。原脚本和任意自定义图形能力保留。
- 金额、币种、股数、每股值、比例及百分点分别表达；规范值不再按 raw_unit 二次换算。保留精度、负数、缺失和来源，不做隐含汇率转换。已知模型结果单位由计算字段及原模型 amount_scale 确定，不根据金额大小猜测。
- spec/overrides 数值位置接受 fact_id/record_id，复用已有绑定实现；来源、原值、期间和实际/预测身份随值继承。计算工具列出真实可用运算，支持研报记录引用，纠正百分比说明。
- 三组共用基础交付、字体、脚本修复和单位能力。新功能不新增模型复核轮次或人工检查点。

## 对照方案

A：通用 Pi + 原文/Python；B：通用 Pi + 同一份已准备记录；C：金融项目工具及技能。主对照是 B/C，A 用来观察结构化准备的作用。模型、推理路由和用户问题相同；各组获得同一基础交付能力，C 特有金融计算、业务技能与来源绑定。CPA 货币价格未经核实，不以目录价当账单。

新资料只入库一次，两篇各建可见会话，准备开销单列；分析时禁止再次入库或修改记录。准备完成后冻结记录内容；所有组可读原始页表，只有 B/C 可查规范记录。新旧研究成果不混用；每个重复使用独立会话，局部更新沿用本次初建会话。

题目：1）中报利润、现金转化及现金流归因；2）研报预测与历史身份、PE 估值和原报告 DCF 复算；3）该 DCF 的局部参数更新与顺序归因。C/B 各独立重复两次，A 各一次，共 15 个任务。这是小规模筛查，不作显著性声明；比较分题列示，不用总体平均掩盖重大错误。

验收主项是来源、口径和关键数值正确，尤其图、表、正文一致；其后比较输入、输出、请求次数、脚本重复、失败返工及时间。原报告内部冲突应揭示并明确采用口径，不把接近目标价当作方法一致。计算器结果、下载可用、程序测试通过都不能单独代替交付验收。

所有原始尝试、失败、中断、未知用量和人工干预留在记录中。没有完成的新试验明确标未运行；未经评测不得宣布金融组胜出。若环境问题导致不能运行，保留全部准备和恢复入口。

## 后续续跑与CPA诊断

用户已批准资料准备使用GPT-6.1 Sol，正式分析仍统一GPT-6 Luna；同时提出CPA可能不稳定。通过Pi原生Responses适配器，对两种模型执行相同JSON以及合成取数/换算/提交小任务，共8次请求均HTTP 200且收到response.completed；工具参数与单位换算正确。证据为 `cpa-stream-probes.json`，仅能确认这些短请求成功，不能证明长任务稳定、上游实际模型身份或排除偶发故障。

CPA现存10份当日错误日志均对应早期HTTP 400。此前最后两次任务的模型用量记录完整，末条stop，未命中32,768输出上限；但旧日志没有逐请求HTTP和流终止元数据，不能据此把所有未完成都归因于模型。现于既有请求审计增加状态码、上游请求/响应ID、终止事件及原因，并正确读取Responses的reasoning.effort；不记录凭据、不新增模型步骤、不改Pi循环。

临时重启Docker时又遇到旧Secrets Engine socket。系统拒绝重命名，自动审批拒绝删除零字节engine.sock；Docker已退出，等待用户按提示手动处理。准备工作先继续研报正文观点，不依赖沙箱；数值清洗和真实对照仍待环境恢复。

用户手动Remove-Item报告PathNotFound，系统目录枚举仍能看到特殊重解析点。重启最新日志又在dockerInference报ERROR_CANT_ACCESS_FILE。经核对两个通信目录都仅含零字节socket，停掉Docker后将目录本身完整改名保留，再启动，Docker引擎29.0.1恢复。采用的是[Docker问题库同类报告中的目录保留办法](https://github.com/docker/for-win/issues/15064)，本机已实测引擎响应；报告不是永久修复保证。镜像、容器和卷未删除。所有旧自动启动容器正常停止，试验沿用4GB/2CPU限制；两份数值准备在原会话继续。

恢复后Sol提交财报全部78张候选表、735条记录，研报提交5/95张数值表后正常结束；两者请求均有HTTP 200与response.completed，后者仍属未完成。抽查源单位又发现已提交的35条财报记录沿用英文RMB千元写法，却被程序以倍率1存储；其中一张实际为附注编号列，还需修正语义。已在通用单位解析中支持RMB/HK$/USD等英文千、百万及十亿缩写，并规范RMB为CNY；来源数字仍由程序取数，不硬编码公司或测试答案。64项相关回归通过，包括实际脚本提交后的倍率及原有跨页识别。更新加载到3001，原财报会话仅修正受影响的两张表，研报继续剩余数值准备。该缺陷在正式冻结前发现，准备干预与费用单列；统一展示工具不能自动修复错误的底层记录。
