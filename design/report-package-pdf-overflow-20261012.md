# 报告包 PDF 长表卡死修复

## 本轮确认范围

- 只修报告导出，3001 不重启、不调用模型、不读取封存测试材料、不改 v0.4.0 发布包、不 push。
- 真实复现材料为伊利会话 `b2858f3c-98b9-4eea-9f18-1ac9a7117ac4` 已保存的报告快照，验证写到独立证据目录；不改生产快照或主库。
- `signals` / `signals_signals` 定位单元格最长 12,956 字符，驱动证据接近 2,000 字符。现有 `finish()` 把 HTML 原样交给 Story，且宿主与 Python 都未限制同一会话的并发导出。MCP 超时不能结束原生 PDF 渲染线程。

## 实施

1. Markdown/PDF 使用页码等可读定位及带底稿提示的长文本摘要；工作簿和快照保留原值。
2. PDF 入口统一处理所有 HTML 表格：纯文本单元格上限、宽表分组、重复行标识；原生渲染放到有时限的子进程，超时实际结束进程并保留其他交付文件，避免线程继续占用 CPU/内存。
3. 宿主同会话复用导出 Promise；Python 对实际渲染再拒绝同会话并发，覆盖 MCP 请求超时而子任务未结束的实发路径。
4. 用长单元格、Excel 完整性、宽表、并发、失败后重试做回归；真实快照经 prepare/finish 计时、检查页数，并查看前两页和异常信号页 PNG。

## 不采用

不提高 MCP 超时，不删除完整定位，不缩减底稿范围，不在生产服务上反复点击复现。

## 验收结论

- 原始完整 Markdown 经与宿主相同的 ReactMarkdown / remarkGfm 渲染，5 秒限时仍无 PDF；单取最长一行则 0.895 秒完成，说明问题涉及整表与分页，不能仅归因为单行字符数。
- 仅限制单元格仍可触发 Story 分页重复；最终同时限制 PDF 表格的列数、分段行数和单元格长度，重复表头与行标识。渲染子进程采用独立空输入，避免继承 MCP 输入管道；25 秒超时会实际结束进程，清理半成品并保留 MD、底稿、快照。
- 最终真实回放：prepare 1.456 秒、Markdown 转 HTML 0.541 秒、finish（PDF + ZIP）1.401 秒，全流程 3.398 秒，121 页。39 张底稿表保留，宽表分组使页数较多，本轮不做报告内容裁减。
- 原始快照完全相同；Excel 比较 14,613 个单元格的值、类型和批注，全部相同。前两页、异常信号第 52 页、定位摘要第 63 页均已查看 PNG。
- Python 22/22、Node 4/4、类型检查通过。原版配置能力限制和评测隔离未改动，相关隔离回归通过。
- 3001 保持原 PID 48796，未重启、未构建覆盖运行版本。用户重启后再做生产 HTTP API 验收。
