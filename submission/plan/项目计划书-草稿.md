## 1 项目摘要

研究员问"公司净利润下降了，为什么经营现金流反而上升？"，答案藏在几百页年报的现金流量表补充资料、附注和管理层讨论里。通用大模型直接读 PDF，常见问题有：
- 把期间、合并口径或单位弄混；
- 编出一个看似合理但无出处的解释；
- 文字、表格、图表三处数字互相矛盾。

Finance Agent 把这件事拆成"可核验的研究过程"，分三层：

1. **资料变成资产**：财报经脚本清洗入库为结构化事实。每个数字都带原文页码、表格坐标、期间、口径和单位。
2. **分析先有底稿**：用户提出财报分析问题后，系统先由程序跑完一份分析底稿，内容包括：
   - 关键指标、利润与现金桥、变动归因；
   - 异常信号；
   - 对应的管理层原文；
   
   然后再交给大模型解释和判断。
3. **交付经过检查**：计算在断网沙箱中执行。答案、表格、图表引用同一组数值。交付前自动检查以下几类问题：
   - 方向措辞（如"增加 -5%"）；
   - 期间顺序；
   - 瀑布图几何；
   - 估值小节的完整性。

我们用三组对照的双盲评测衡量这套设计：原版通用智能体、同数据通用智能体、金融智能体，三组使用同一模型、同一材料、同一题目。评分由两位独立评审完成，第二位按倒序评阅，分数封存后再揭盲。我们同时报告正面和负面结果。【待填：v3 正式评测的一句话结论】

## 2 背景与问题

### 2.1 财报分析为什么难

- **资料异构**：
  - 年报动辄 200–300 页；
  - 表格经常无框线、跨页续表、合并单元格；
  - 同一指标在不同表里口径不同，比如合并与母公司、归母与少数股东、扣非与非扣非；
  - 单位混用元、万元、百万元。
- **结论必须可核验**：投研结论要能回到原文页码和计算过程。没有出处的数字在研究中不能用。
- **交付一致性**：研究成果通常同时包含文字、表格和图表，任何一处数字或方向写错都是实质错误。

### 2.2 我们在开发中实际观察到的问题

以下都是项目评测中记录到的真实缺陷，用于说明设计动机：

| 现象 | 实例（来自盲评记录） |
|---|---|
| 期间顺序颠倒 | "合并净利润由 8,463.7 降至 10,284.3"，正确应为由 10,284.3 降至 8,463.7 |
| 关系方向写反 | 质保费用由销售费用重分类进成本后，毛利率和销售费用率同向下降，报告却写"方向相反" |
| 图表几何错误 | 瀑布图的负值柱被重复下移，累计桥断裂 |
| 序列错位 | 图中把"归母净利润"和"经营现金流"两个值互换 |
| 单位失配 | CSV 数值是百万元，却标为亿元，相差 100 倍 |
| 工具不被使用 | 金融工具已经存在，模型却自己手写计算或绘图，绕开了已验证的路径 |

结论：只给模型更多工具和提示，不能保证专业性。**必经的程序步骤**和**交付前的确定性检查**才是关键。

|---|---|---|

## 4 解决方案与产品形态

### 4.1 工作台

- **项目**：一家公司或一个研究主题。同一项目内的会话共享资料，不同项目之间隔离。
- **会话**：一次研究任务。会话内展示执行过程、工具调用、授权卡片和用量。
- **附件流向**：显示每份资料被如何处理、存到哪里、被哪次分析引用。
- **资产看板**：展示已入库的财务事实、研报预测、观点和保存的模型，可跳转到原文定位。

### 4.2 一次分析的完整流程

1. **入库**：
   - 解析 PDF 并识别候选表；
   - 模型编写清洗脚本，在沙箱中运行，按原格坐标取数；
   - 主体、期间、单位、维度检查通过后，事务式提交；
   - 断点和用量都持久化，中断后可以续跑。
2. **必经底稿**（金融层）：识别为财报分析请求后，宿主先运行底稿流水线，产出：
   - 利润与现金桥、变动归因；
   - 异常信号与追问字段；
   - 管理层原文（附页码）；
   - 口径未齐标记、缺失项及原因。
3. **模型分析**：模型读取底稿后补充取数和计算，按三层结构撰写解释。三层依次是：
   - 披露事实（附原文页码）；
   - 量化影响；
   - 标注为推论的判断。
4. **统一数值交付**：每个数值只换算一次单位，同一组结果生成 CSV、图表和报告占位符。
5. **交付检查**：
   - 方向词与符号、期间顺序、关系断言；
   - 瀑布图连续性；
   - 估值小节完整性；
   - 无法确认的内容给提示，而不是静默通过。
6. **留痕**：保留以下记录，满足"可核验、可追溯、可复现"：
   - 文件访问、工具调用、沙箱脚本、输入输出哈希；
   - 每轮 token 用量。

## 5 技术方案

### 5.1 系统架构

【图：系统分层与信任边界，复用 `paper/v0.3.0/architecture.svg`，并补画 v3 的底稿流水线与交付检查】

| 层 | 技术 | 职责 |
|---|---|---|
| 界面 | React 19、TypeScript、Vite | 项目和会话、附件流向、资产看板、授权卡片、用量明细 |
| 宿主 | Express（TypeScript）、Pi SDK 原生会话 | 任务生命周期、上下文与压缩、重试恢复、工具白名单、请求识别与底稿注入 |
| 领域服务 | Python 3.12、MCP（stdio） | 文档解析、脚本清洗、结构化事实、底稿流水线、金融模型、交付检查 |
| 存储 | SQLite + FTS5、原件文件库 | 事实与证据分层，版本化研究资产 |
| 沙箱 | Docker | 断网、只读根文件系统、非 root、2 CPU / 2 GiB、单次 120 秒；执行模型写的代码 |

对应竞赛要求的五个模块：

| 模块 | 实现 |
|---|---|
| 任务编排 | Pi 会话，加宿主的长任务检查点 |
| 工具调用 | MCP 领域工具，三组配置分别为 10 / 13 / 32 个工具 |
| 提示指令 | 稳定前缀的系统提示，加金融技能文件 |
| 数据处理 | 解析、脚本清洗、底稿流水线 |
| 日志记录 | 审计 JSONL、用量账本、产物清单与哈希 |

### 5.2 关键技术

1. **脚本清洗替代逐条转写**：
   - 模型不再逐个抄写数字，而是写一段映射脚本；
   - 程序按原格坐标取数，再检查主体、期间、单位、维度；
   - 减少转写错误，也减少输出 token。
2. **财务事实的数据模型**：每个事实都记录以下字段，研报预测与公司披露分开存储，预测不能冒充披露：
   - 主体、期间、口径、维度、单位；
   - 来源页码和表格坐标、处理版本。
3. **必经底稿流水线**（v3 新增）：
   - 背景：历次评测发现"有工具不等于会用工具"，例如变动归因工具在财报题中两次都没有被调用；
   - v3 改为宿主在推理前直接运行流水线，模型拿到的是成品底稿；
   - 底稿紧凑，完整表以句柄方式按需读取。
4. **管理层解释对齐与信号追问**：
   - 对每个主要变动和异常信号，程序检索管理层原句，附页码；
   - 要求给出替代解释，例如季节性、备货、回款节奏、一次性因素；
   - 判断持续性时，样本不足三期不得写"连续"。
5. **统一数值交付**：每个数值只换算一次，CSV、图表、正文用同一组结果，杜绝重复缩放。
6. **交付一致性检查**（v3 / F2.1）：
   - 方向词与带符号数值的矛盾；
   - 期间顺序，如"由 X 降至 Y"要求 X > Y；
   - 关系断言，如"方向相反"；
   - 瀑布图链式连续性；
   - xlsx 字符串单元格也纳入检查；
   - 无法自动判定的情况只提示、不阻断。
7. **长任务与成本控制**：
   - 交给 Pi 原生的压缩与重试；
   - 业务进度另行持久化，断点续跑；
   - 稳定前缀提高缓存命中；
   - 用量逐请求记账，未知用量单列。

## 6 创新点

1. **"程序先跑、模型拿成品"的金融层**：
   - 专业流程不靠模型自觉调用工具，而由宿主强制执行；
   - 金融规则放在领域层，不改通用 Agent 主循环。
2. **证据与数值的强绑定**：
   - 数字能回溯到页码和表格坐标；
   - 文字、表格、图表共用同一组数值；
   - 交付前做确定性检查。
3. **可复现的三组双盲评测体系**：
   - 三组分别是原版 Pi、同数据通用组、金融组；
   - 控制条件：同模型、同题、隔离会话；
   - 评审流程：附件匿名化后核对，两位评审独立评分，第二位倒序，分数封存后才揭盲；
   - 保留失败、缺失和未知用量；
   - 能分别回答两个问题：整个系统比原版 Pi 好多少，金融层自身贡献多少。
4. **以负面结果驱动迭代**：
   - 每轮评测的缺陷按"金融层自身引入 / 模型共性 / 交付基建"归因，只修有证据的问题；
   - 门槛不达标就先停下诊断，不继续堆功能。

## 7 评测设计与目前结果

### 7.1 评测设计

- **材料**：
  - 开发集：卡罗特 2025 中报、伊利 2024 年报、海尔智家 2024 年报；
  - 新 held-out：白云机场 2024 年报，评测前对开发者封存。
- **三组对照**：

| 组别 | 工具数 | 说明 |
|---|---:|---|
| 原版 Pi | 10 | 通用提示和原始工具 |
| prepared | 13 | 同一份结构化数据，加通用交付支持 |
| financial | 32 | prepared 的全部内容，加金融层（底稿、金融工具、技能） |

- **题型**：
  - 业绩与现金流解释（D1）；
  - 现金流桥与盈利质量（X3）；
  - 会计重分类及可比口径（X7）；
  - held-out 三题（BH1–BH3）。
- **评分维度**：
  - R1 读取；
  - R2 实质正确；
  - R3 解释；
  - R4 调整；
  - R5 异常；
  - R6 通用交付质量；
  - 另计实质缺陷，同机制跨文件只记一次。
- **成本**：已知输入和输出 token、请求数、未知用量（单列）。资料准备成本另计。

## 11 风险与对策

| 风险 | 对策 |
|---|---|
| 模型幻觉或错误解释 | 底稿先行、原文对齐、交付检查；输出中区分事实、计算和推论 |
| 数据安全与合规 | 本机运行，沙箱断网，密钥由系统加密（Windows DPAPI）；原件与数据库不上传，只有任务所需片段发给用户选定的模型服务 |

| 泛化不足 | 用封存的 held-out 公司检验；新增行业样本按同协议复验 |
| 评测偏差 | 盲评、倒序复评、封存后揭盲；缺失与未知用量照实报告 |
